## Release definition

v0.4.0 is the **evidence-integrity and useful-detection release**.

The release is ready when a project owner can run one scoped audit and trust all of the following:

1. A retest cannot call findings `fixed` when the baseline belongs to another project, an
   incompatible rule revision, or a check that did not run.
2. Network, parser, traversal and external-tool failures are visible as incomplete evidence; none
   are converted into a pass or a confirmed vulnerability.
3. Security exposure, supply-chain risk, search discoverability, reliability and evidence integrity
   are reported separately. A HIGH discoverability impact is not presented as a HIGH security
   vulnerability.
4. Every audit records what it discovered, scanned, excluded, skipped, truncated and failed to
   inspect.
5. Report files from every audit surface use the same private, atomic and non-overwriting writer.
6. The built-in narrow source rules are supplemented by real, pinned integrations for secret and
   dependency-vulnerability detection without silently downloading or executing tools.
7. Claims are backed by planted fixtures and five fixed-commit ordinary open-source project runs.
8. The released archive, installer, Action, schemas, migration documentation and public claims all
   describe the same behavior.

v0.4.0 is **not** a general SAST/DAST scanner, an authenticated pentest, an automatic authorization
reviewer, or proof that a project is secure. API authorization, business logic, OAuth/OIDC, LLM,
database isolation and most deployment review remain agent-guided unless a separately named,
regression-tested adapter covers a narrow check.

## Planning audit baseline

The v0.3.0 productization and adoption programs established a real CLI, schemas, reports, lifecycle,
Action, signed release and evidence-led public surfaces. The following gaps are release blockers for
v0.4.0 because they affect the truthfulness of a result rather than its presentation.

| Priority | Reproduced or inspected gap | Required v0.4.0 outcome |
|---|---|---|
| P0 | A report from project A can be passed as project B's baseline; absent fingerprints become four `fixed` results and the retest exits `0`. | Subject and ruleset identity must be compatible before comparison. A mismatch exits `2` and produces no `fixed` claim. |
| P1 | An unreachable crawl target can produce `robots-missing`, `sitemap-unreachable`, `sitemap-empty` and `baseline-fetch-failed` as HIGH findings even though the evidence source was unavailable. | Crawl findings use the common state/domain schema. Unavailable evidence is `unknown`, never confirmed, and exits `3` when no confirmed threshold breach exists. |
| P1 | Source traversal stops at depth 5 or 5,000 files and silently skips unreadable, over-1 MiB and malformed candidate files. | A coverage ledger records limits and skipped evidence. Relevant truncation or parsing failure makes the run incomplete and non-zero. |
| P1 | The demo's 13 HIGH findings combine 2 security exposures with 11 search/discoverability failures. | Public and machine reports summarize by risk domain and evidence state before severity. |
| P1 | Source reports are private, while crawl and AWS helpers use default directory/file permissions and direct writes. | Every evidence-producing command uses one private, atomic, refusal-to-overwrite path and sanitized evidence contract. |
| P2 | The capability total combines detection, reporting, demo, installation and distribution automation, which can imply more vulnerability coverage than exists. | Capability records separate detection, evidence infrastructure, distribution and agent-guided methodology. No aggregate automation count is used as a coverage claim. |
| P2 | Capability and release surfaces have factual drift, including stale AWS-fixture language and inconsistent treatment of planned adapters. | Structured claims fail CI when evidence, maturity, category or release state disagrees. |

The earlier external audit claims that the repository has one squash commit and that current tests
fail on macOS/Node 24 are not part of this baseline: both were rechecked and disproved. The planning
baseline is limited to defects that were reproduced or directly inspected in the current tree.

## Decisions fixed for this plan

- Report and finding contracts move to schema version 2. Version 1 remains readable for display and
  explicit migration, but it is never silently accepted as a comparable v2 retest baseline.
- Risk domains are `security_exposure`, `supply_chain`, `search_discoverability`, `reliability` and
  `evidence_integrity`. Severity is interpreted inside a domain; summaries and CI policy retain the
  domain.
- Result states remain `confirmed`, `suspected`, `unknown` and `not_applicable`.
- Baseline states become `new`, `unchanged`, `regressed`, `fixed`, `unretested` and
  `not_comparable`. `fixed` requires affirmative evidence that the same compatible check completed
  against the same subject and no longer found the condition.
- Exit codes are stable across audit commands: `0` complete/no configured confirmed threshold;
  `1` a confirmed finding crosses the configured domain/severity threshold; `2` invocation,
  schema, authorization or identity contract error; `3` no confirmed threshold breach, but required
  evidence is incomplete or unknown. A confirmed threshold breach takes precedence over an
  unrelated unknown so CI does not hide a demonstrated failure.
- The zero-dependency built-in path remains available. External adapters are discovered explicitly
  and never downloaded or executed without a user/CI installation step.
- Gitleaks and OSV-Scanner are required v0.4.0 adapters. Semgrep may ship as experimental only if it
  passes the same adapter and fixture gates; it is not required for release. ZAP remains deferred
  because its active-testing and target-authorization model needs a separate design.
- v0.4.0 does not depend on star count, post reach, upstream acceptance or invented user studies.

Changing one of these decisions requires a documented M0 amendment, its consequences for later
acceptance tests, and an owner decision before implementation continues.

## Program rules

1. Work through M0-M8 in order. A later milestone may be prototyped, but it cannot be marked complete
   while a dependency is incomplete.
2. Every bug fix starts with a regression that demonstrates the pre-fix failure. Every new detector
   has a planted positive, negative, unavailable/malformed and redaction path.
3. After each milestone: update this file, run focused tests and `npm run check`, run the Skill
   validator, run `git diff --check`, commit, push, wait for CI and CodeQL, then record the exact
   commit and run URLs before starting the next milestone.
4. Do not weaken passive defaults or authorization gates. Source-only fixtures and owned loopback
   services are preferred. No third-party deployment is probed for release evidence.
5. Do not store secret values, authorization headers, cookies, private source excerpts, raw AWS
   error payloads or sensitive absolute paths in reports.
6. Generated public counts and claims must come from structured evidence. A demo animation or
   release note cannot maintain an independent count.
7. External tools must be version-recorded, output-parsed from a structured format, covered by
   malformed-output tests and treated as `unknown` when absent or unusable.
8. Keep `SKILL.md` procedural and concise through progressive disclosure. Detailed adapter,
   migration and report contracts belong under `docs/` or `references/`.
9. No milestone completion record may claim external validation, publication, security disclosure
   or adoption unless the corresponding evidence exists.

## M1 - Baseline identity and honest retest

### Deliverables

- Give each scope a privacy-preserving `subject.id` and `scopeDigest`. Prefer a persisted explicit
  project ID; use a documented local derivation only when no persisted scope exists.
- Record `ruleset.digest`, adapter IDs/versions, rule revisions and fingerprint versions.
- Reject a different subject or incompatible scope before comparison with exit `2` and no report
  bundle claiming fixed results.
- Compare compatible rules individually. New rules may be `new`; disabled, missing or failed rules
  become `unretested`; incompatible rule revisions become `not_comparable`.
- Permit v1 migration only through an explicit command that binds the old report to the reviewed
  project/scope and records migration lineage. Never mutate the original baseline.
- Ensure a project move or fresh clone has an intentional rebind path instead of encouraging users
  to edit report JSON.

### Required regressions

- Project A baseline used against project B.
- Same project path replaced with different source/scope identity.
- Compatible rule added, rule removed, adapter unavailable and rule revision changed.
- Baseline tampering, duplicate fingerprints and forged tool/ruleset metadata.
- Valid same-project unchanged, fixed and regressed paths.

### Acceptance

- No absent, unexecuted or incompatible check can produce `fixed`.
- Cross-project and tampered baselines exit `2` before output is committed.
- Every `fixed` result links to compatible prior/current check evidence and successful current
  coverage.
- Old v1 evidence remains viewable, and migration preserves the original digest and provenance.

### Stop condition

Stop if compatibility has to be weakened to make historical demo fixtures pass. Migrate the fixture
or start a new baseline instead.

## M2 - Unified semantics across audit surfaces

### Deliverables

- Route project source, crawl, crawler identity, edge and AWS findings through the v2 finding/report
  constructors. Raw observations may remain tool-specific, but conclusions must share the schema.
- Require every conclusion to carry `domain`, `severity`, `state`, rule identity, sanitized evidence,
  remediation and retest instructions.
- Replace crawl/AWS ad hoc counts and exits with the shared summary and exit-policy implementation.
- Distinguish a missing control from an unreachable evidence source. For example, an HTTP 404 may
  confirm absence only after transport/origin identity succeeds; status `0` is unknown evidence.
- Define precedence when confirmed and unknown results coexist and expose both in every renderer.
- Add an `audit policy` record so reports show which domains and severities could fail CI.

### Required regressions

- Entirely unreachable crawl origin, timeout after partial success and malformed sitemap.
- AWS top-level and nested permission denial, missing CLI and malformed JSON.
- Edge verifier without required curl/TLS capability.
- A run containing both a confirmed HIGH security exposure and unrelated unknown evidence.
- Schema equivalence checks across JSON, Markdown, HTML, SARIF and JUnit.

### Acceptance

- The unreachable crawl fixture has no confirmed `robots-missing`, `sitemap-empty` or equivalent
  security/discoverability conclusion and exits `3` in the absence of another threshold breach.
- Exit `1` always points to at least one confirmed finding in the configured domain/severity policy.
- Exit `3` always points to at least one explicit unknown/incomplete coverage record.
- No renderer drops domain, evidence state or baseline state.

### Stop condition

Do not retain a legacy report path merely to preserve old demo counts. Compatibility applies to
inputs and migration; new conclusions must use the common contract.

## M3 - Coverage ledger and fail-closed traversal

### Deliverables

- Replace silent source walking with an adapter-aware coverage ledger containing discovered,
  eligible, scanned, excluded, skipped, truncated and error counts.
- Record bounded reason codes and sanitized sample paths for policy exclusions, depth/file/size
  limits, unreadable files, unsupported encodings and parse failures.
- Treat an expected policy exclusion differently from a relevant candidate that could not be
  inspected.
- Make traversal limits configurable within bounded values and record the effective limits.
- Emit a dedicated `evidence_integrity` unknown when an eligible security input was truncated or
  unreadable. A zero-finding partial scan cannot exit `0`.
- Record rule and adapter coverage even when they produce no findings.

### Required regressions

- Monorepo deeper than five levels and larger than 5,000 files.
- Relevant candidate just beyond the configured limit.
- Over-1 MiB candidate file, unreadable candidate, malformed `package.json` and symlink escape.
- Ignored dependency/build tree that should be an intentional exclusion rather than an unknown.
- Empty supported project, unsupported project and complete no-finding project.

### Acceptance

- For every supported adapter: `eligible = scanned + skipped/error` is reconcilable from the report.
- Hitting a limit is visible in JSON and human reports and returns `3` when it affects required
  evidence.
- A complete, supported, no-finding project can still return `0`, with coverage proving that the
  relevant checks actually ran.
- Large-project traversal stays bounded and deterministic on repeated runs.

### Stop condition

Stop adding source rules if the traversal layer cannot prove whether their candidate files were
actually inspected.

## M5 - Private atomic evidence handling

### Deliverables

- Introduce one shared evidence writer for project, crawl, crawler, edge and AWS outputs.
- Create report directories as `0700` and files as `0600` where the platform supports POSIX modes.
- Write to exclusive same-directory staging files, validate complete content, then atomically rename.
- Refuse overwrite, symlink targets and output escape; preserve prior evidence on interruption or
  renderer failure.
- Centralize evidence redaction and bound strings/arrays before rendering.
- Ensure AWS account/user/bucket/security-group identifiers and external-tool results receive an
  explicit sensitivity treatment. Do not persist raw stderr by default.

### Required regressions

- Permission assertions for every output-producing command on macOS/Linux.
- Existing-file collision, symlink destination, renderer exception and simulated interrupted write.
- Secret/cookie/token/email/private-key sentinels across JSON, Markdown, HTML, SARIF, JUnit and
  console output.
- Hostile HTML/XML/control characters and oversized external-tool messages.

### Acceptance

- All sensitive report bundles are private, atomic and non-overwriting.
- A failed multi-render operation leaves either the complete previous bundle or no committed new
  bundle, never a misleading partial set.
- No test sentinel appears in committed report files or normal console output.

### Stop condition

Do not integrate external scanners until their output can pass through this writer and redaction
contract without persisting raw secrets.

## M6 - External adapter protocol and useful detection

### Deliverables

- Define a documented adapter protocol: ID/version discovery, applicability, rule inventory,
  invocation, timeout, structured parsing, redaction, coverage, findings and failure state.
- Add `webapp-security doctor` or an equivalent read-only command that reports available adapter
  versions and unsupported/missing prerequisites without downloading anything.
- Integrate Gitleaks for repository/working-tree secret detection. Store only redacted fingerprints,
  rule IDs and locations; never secret values.
- Integrate OSV-Scanner for supported lockfile/SBOM dependency vulnerability detection. Preserve
  ecosystem/package/advisory identity while avoiding credentials and unsupported severity guesses.
- Record exact tested versions and verify tool identity before parsing output. Missing executable,
  unsupported version, timeout, non-zero internal error or malformed output becomes adapter
  `unknown`, not a clean scan.
- Add opt-in adapter selection and a deterministic built-in-only mode.
- Extend the GitHub Action with a backward-compatible source-audit mode and stable SARIF/report
  outputs. Existing crawl-mode inputs remain regression-tested.
- Resolve Issue #7's alert ownership, triage and update policy before making dependency/secret
  results a CI gate.
- Evaluate Semgrep behind the same protocol. It may be labelled `experimental` only with pinned
  ruleset identity and planted fixtures; otherwise document it as deferred. Do not add ZAP in this

## Definition of done

v0.4.0 is complete only when M0-M8 are complete and the published immutable release demonstrates
the release definition at the top of this document. In practical terms, the minimum product at that
point is:

- a trustworthy v2 evidence model, not merely more report fields;
- retest identity that cannot manufacture a fix across projects or incomplete checks;
- complete/partial/unavailable scan accounting;
- separate security, supply-chain, discoverability, reliability and evidence-integrity reporting;
- private atomic evidence across all commands;
- built-in narrow rules plus real Gitleaks and OSV-Scanner adapters;
- five fixed-commit real-project records and planted regressions for every advertised detector;
- backward-compatible crawl Action behavior plus a tested source-audit path;
- signed, reproducible, attested release artifacts and verified installation/upgrade;
- honest public claims that still state the agent-guided and unsupported boundaries.

Star growth, community posts, five usability sessions, npm publication, a Semgrep adapter, a ZAP
integration or an upstream project's acceptance are not v0.4.0 completion requirements. They may be
recorded if they actually occur, but they cannot substitute for any release gate above.

## Deferred beyond v0.4.0

- Authenticated DAST and ZAP orchestration with target-safe active-test policy.
- Deterministic BOLA/IDOR and business-logic testing across arbitrary frameworks.
- Native Windows/PowerShell lifecycle unless a maintained test environment is added.
- Automatic download/installation of external scanner binaries.
- A precision/recall headline before the labelled corpus is large and representative enough.
- Automatic application of security patches without review and retest.
