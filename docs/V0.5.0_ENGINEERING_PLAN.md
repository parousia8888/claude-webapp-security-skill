## Release definition

v0.5.0 is the **source detection and understandable remediation release**.

The release is ready when a Web project owner without a security background can run one scoped
audit and answer all of these questions without reading raw scanner output:

1. What did the audit actually inspect, and what could it not inspect?
2. What is the professional name of each issue, and what does it mean in ordinary language?
3. What concrete evidence exists, and is the conclusion confirmed, suspected, unknown or not
   applicable?
4. What could realistically happen if the issue remains?
5. What change is proposed, which alternatives exist, and which user decision is required?
6. What behavior could the fix break or alter?
7. How will both security and normal product behavior be retested, and when should the change be
   rolled back?

v0.5.0 also expands deterministic source detection beyond the four v0.4.0 risk checks. The built-in
stable path concentrates on JavaScript/TypeScript and Python Web projects. Other languages may
receive findings from an optional mature SAST adapter, but they are not advertised as having equal
built-in coverage.

## Product audience and operating model

The primary user builds or maintains a Web product with an AI coding agent and may not know how to
interpret terms such as XSS, command injection, CORS, insecure deserialization or session fixation.
The product must preserve the technical term and standards references while explaining the same
finding in concrete product language.

The operating model is:

```text
deterministic observation or pinned scanner lead
  -> evidence state and confidence boundary
  -> technical and plain-language explanation
  -> reviewable proposal and alternatives
  -> user decision where product behavior changes
  -> patch only when authorized
  -> security retest plus project-native functional tests
  -> keep or roll back based on recorded criteria
```

AI-generated interpretation remains a proposal. A source pattern, external scanner match, standards
mapping or AI judgment cannot by itself become a confirmed vulnerability.

## Audit baseline

### Current v0.4.0 capability

The v0.4.0 repository provides strong scope, authorization, evidence-state, coverage, report,
retest, release and supply-chain contracts. It has stable Gitleaks and OSV-Scanner adapters and
separate crawl, edge, crawler-identity and AWS rule families. Its source-code vulnerability
detection remains narrow.

| Surface | v0.4.0 observed state | v0.5.0 consequence |
|---|---|---|
| Built-in source inventory | 6 rules; 4 risk checks and 2 evidence-integrity checks | Expand real source-risk families and continue reporting integrity rules separately. |
| Source languages | Node/Python project discovery; few language-specific checks | Deepen JavaScript/TypeScript and Python only for this release. |
| Finding explanation | Title, severity, state, summary, evidence, remediation and retest | Add a structured professional/plain-language, consequence, proposal, side-effect, decision and rollback contract. |
| Evidence model | v2 subject/ruleset identity, coverage and honest retest | Preserve semantics and introduce a versioned v3 migration path. |
| External source tools | Stable pinned Gitleaks and OSV; Semgrep deferred | Benchmark Semgrep CE and Opengrep, then promote at most one stable SAST adapter. |
| Deployment configuration | Discovery records Docker/IaC inputs; no stable policy scanner | Benchmark Trivy and Checkov, then promote at most one stable configuration adapter if it passes the gate. |
| Automatic patching | Patch text is review evidence; no broad automatic application | Keep proposal/application separate; do not promise unattended project modification. |

| GitHub trust surface | Signed v0.4.0, SBOM, checksum, provenance, verified installer and `v1` | Reuse the release chain and add exact v0.5.0 consumer evidence. |

The weakness is source vulnerability detection, not total repository rule count. Crawl rules,
renderers, installers, release automation and documentation must never be used to inflate source
detector claims.

### Standards and research basis

Rule priority and explanation metadata use:

- OWASP Top 10:2025 for current Web risk categories;
- OWASP ASVS 5.0.0 for versioned verification requirements where an exact requirement applies;
- OWASP API Security Top 10:2023 for API authorization, resource consumption and flow risks;
- CWE Top 25:2025 and individual CWE entries for implementation weakness names;
- NIST SSDF 1.1 for release and remediation-process requirements;
- SARIF 2.1.0 for machine-readable rule descriptions, help text and help URIs.

Standards identifiers classify and explain evidence. They do not prove exploitability and do not
automatically determine local severity.

Published and preprint research on AI-assisted secure coding, vulnerability detection and repair
shows three recurring limitations: generated code can contain common weaknesses, users can be
overconfident in generated code, and a patch can satisfy a security oracle while breaking ordinary
behavior. The product consequence is fixed for this release: every applied security patch needs a
security-specific retest and the project's normal functional tests; a build alone is insufficient.
Preprints may inform engineering decisions but are not presented as settled efficacy claims.

| Product family | Strength relevant to v0.5.0 | Boundary for this project |
|---|---|---|

| Bearer | Broad application-security rule catalogue and data-flow orientation | Useful comparison; do not copy claims or rule text without compatible licensing and local regressions. |
| Trivy / Checkov | Mature Docker, IaC, Kubernetes and workflow configuration checks | Select at most one adapter and retain scanner matches as suspected leads. |
| ZAP / Nuclei | Runtime and template-driven probing | Authenticated DAST is deferred because authorization, test accounts and destructive-request control need a separate contract. |
| Trail of Bits skills / reverse-skill | Specialist breadth, tool orchestration and strong security workflows | Keep this project's scope narrower: beginner-facing Web hardening, evidence integrity and retest closure. |

The architectural conclusion is a hybrid: a bounded set of high-confidence built-in checks, one
pinned mature SAST adapter, optionally one pinned deployment/IaC adapter, and agent-guided context,
explanation and proposals. Adding a large unlabelled regex collection is not an acceptable path to
a higher rule count.

## Decisions fixed for this plan

1. **Language depth:** stable built-in source rules target JavaScript/TypeScript and Python. Other
   languages remain agent-guided or depend on the selected SAST adapter.
2. **Schema:** deterministic source reports move to finding/report schema v3. v2 remains readable.
   A v2 baseline may be compared only through an explicit, tested compatibility path that preserves
   subject, scope, rule revision and coverage semantics; otherwise it is `not_comparable`.
3. **Evidence states:** `confirmed`, `suspected`, `unknown` and `not_applicable` retain their v0.4.0
   meanings. Syntax/sink patterns and all external scanner matches default to `suspected` unless an
   independently reproduced execution path satisfies a rule-specific confirmation contract.
4. **Explanation:** every actionable finding carries structured technical and plain-language
   explanations, realistic consequence, evidence boundary, proposal, alternatives, side effects,
   functional and security retests, rollback conditions and user-decision fields.
5. **Rule counting:** public counts separate built-in risk rules, evidence-integrity rules, external
   adapter rules and agent-guided methodology. Detector families and individual rules are both
   reported; no total combines unrelated capability categories.
6. **Built-in target:** add 15-25 stable, useful source-risk rules only when each passes the fixture
   and explanation gates. The number is a planning range, not a release gate. Precision and honest
   evidence take precedence over reaching the upper bound.
7. **External SAST:** Semgrep CE and Opengrep are benchmark candidates. Only one may be marked stable
   in v0.5.0. If neither passes licensing, reproducibility and evidence gates, both remain
   experimental/unavailable and the release may proceed without claiming mature SAST coverage.
8. **Deployment/IaC:** Trivy and Checkov are benchmark candidates. At most one becomes stable under
   the same gate. This adapter is desirable but not allowed to delay or weaken the core explanation
   and source-rule release.
9. **Patch behavior:** the product may generate a reviewable patch proposal. It does not silently
   apply changes to authentication, authorization, public access, data handling or production
   configuration. Those changes require an explicit user decision.
10. **Test budget:** use one planted positive and one meaningful negative per stable rule, targeted
    malformed/unavailable tests at shared parsers, representative renderer tests and one bounded
    ordinary-project pass. Do not create combinatorial framework matrices without a reproduced risk.
11. **Publication authorization:** the owner has approved completing the signed `v0.5.0` Release and
    moving `v1` after all gates pass. Stop automatically if GitHub requires a new human-only security
    action or if immutable identities disagree.

Changing decisions 1-9 requires an amendment in the M0 completion record before dependent work
continues. Test scope may be reduced when equivalent evidence already exists, but no stable detector
may lose its positive and negative regression.

### Stable-rule promotion states

| State | Meaning | Public treatment |
|---|---|---|
| `candidate` | Proposed rule with a written threat and detection boundary, but incomplete implementation evidence. | Plan only; unavailable. |
| `experimental` | Runnable behind an explicit opt-in boundary with incomplete precision, compatibility or maintenance evidence. | Excluded from stable counts and default gates. |
| `stable` | Registry-complete, deterministic, positive/safe-neighbour tested, sanitized and covered by the release compatibility contract. | Included in exact stable counts. |
| `rejected` | Evaluated but unsuitable because the signal is too noisy, unsafe, legally unclear or operationally unbounded. | Record rationale; do not execute or count. |
| `deferred` | Plausible but requires data flow, runtime context, ownership decisions or maintenance work outside v0.5.0. | Agent-guided or future work only. |

The required finding explanation field names are frozen as `technicalTerm`, `plainLanguage`,
`consequence`, `evidenceBoundary`, `standards`, `proposal`, `alternatives`, `sideEffects`,
`securityRetest`, `functionalRetest`, `rollback` and `userDecisions`.

## Program rules

1. Execute M0-M9 in order. Later work may be investigated, but cannot be marked complete while a
   dependency remains incomplete.
2. Before implementation, reproduce or statically demonstrate the gap. Do not manufacture a defect
   merely to satisfy the plan.
3. Every stable new detector has a vulnerable fixture, a safe near-neighbour fixture, sanitized
   evidence, applicability accounting and an explicit confirmation boundary.
4. Every shared parser/adapter has missing tool, wrong version, timeout or malformed-output coverage
   where the failure is technically possible. Equivalent existing protocol tests may be reused.
5. Every milestone updates this file with implementation, tests, commit, CI/CodeQL links and
   remaining risks. Run focused tests during iteration; run `npm run check`, Skill validation,
   structured-file parsing and `git diff --check` once on the milestone candidate. Remote CI owns
   the full OS/Node matrix.
6. Preserve passive defaults, scope/authorization gates, private atomic evidence, refusal to
   overwrite and secret redaction.
7. Do not execute project dependencies, send source to a hosted scanner, or probe a third-party
   deployment for release evidence.
8. Keep `SKILL.md` procedural and below its context budget. Put rule metadata, explanation detail,
   adapter contracts and migration material in directly linked `docs/` or `references/` files.
9. Public claims come from structured registries/evidence. Release notes, README and demo cannot
   maintain independent rule counts.
10. A milestone can record a known limitation. It cannot relabel an unavailable check as clean, a
    scanner lead as confirmed, or a documentation example as measured product efficacy.

## M3 - JavaScript/TypeScript built-in rules

### Candidate rule families

Promote only candidates that can be detected with useful precision under the bounded local parser.
Expected candidates include:

- dynamic execution: `eval`, `Function` constructor and string-based process execution leads;
- command execution: child-process shell usage and explicitly enabled shell interpretation;
- browser output: `dangerouslySetInnerHTML` and direct HTML sink leads with evidence boundaries;
- CORS: wildcard origin combined with credentials and dangerous origin reflection configurations;
- session/cookies: hard-coded session/JWT secrets, missing production cookie protections and
  disabling secure defaults;
- JWT: explicitly disabled signature verification, unsafe accepted algorithms or non-expiring token
  configuration where statically visible;
- TLS/client transport: explicit certificate-verification disabling;
- file/path: user-influenced file/path sink leads only when the syntax provides a defensible signal;
- upload: explicitly unbounded or unrestricted upload configuration where framework semantics are
  stable;
- debug/admin exposure: public inspector and framework debug/development server configuration;
- logging: direct logging of known password/token/cookie/auth-header variables as suspected leads;
- cryptography/randomness: MD5/SHA-1 or `Math.random` only in clearly security-named contexts.

Candidates such as generic SQL string concatenation, generic path joins and generic use of weak hash
functions must not be promoted without enough context to avoid common non-security uses. When the
engine cannot prove source-to-sink flow, wording must say `lead` and state `suspected`.

### Deliverables

- Add a syntax-aware or structured-token inspection layer sufficient to avoid comments, quoted
  documentation and generated/minified files where feasible without installing project
  dependencies.
- Add applicability accounting by language, extension and supported configuration file.
- Implement the accepted JavaScript/TypeScript rules and register rejected candidates with the
  reason they were not promoted.
- Produce sanitized path/line and bounded structural evidence; never persist source lines containing
  possible secrets.
- Generate proposals only for narrow configuration changes with deterministic context. Other rules
  provide review instructions rather than unsafe patches.
