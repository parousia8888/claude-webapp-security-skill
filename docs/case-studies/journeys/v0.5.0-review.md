# v0.5.0 ordinary-project source review

This review runs the complete v0.5.0 built-in source path over the same five ordinary projects at
fixed commits used by the v0.4.0 journey corpus. It did not install or execute project dependencies,
contact a hosted project, or use an external scanner. The structured identity and every reviewed
finding ID are in [`v0.5.0-evidence.json`](v0.5.0-evidence.json).

## Result in ordinary language

The rules produced 43 findings. That is **not 43 vulnerabilities**. Manual source review classified
11 as useful leads worth project-owner review, 27 as expected benign matches, one as unknown because
source parsing was incomplete, and four as confirmed missing-lockfile facts in example/helper
packages. No precision or recall percentage is claimed from five projects.

| Project | Report result | Manual review | What the result means |
|---|---|---|---|
| Linkwarden | 6 suspected | 6 expected benign matches | Server-side JSDOM operations, sanitized HTML and repository-owned style content triggered intentionally broad browser-sink rules. |
| Healthchecks | 5 suspected | 4 useful leads; 1 expected benign match | Same-origin AJAX responses inserted as HTML need response-encoding review; the opt-in operator shell integration quotes substituted values. |
| Open WebUI | 6 suspected; 1 unknown | 3 useful leads; 3 expected benign matches; 1 unknown | Plugin code execution and production source maps need ownership/deployment review; one Python file could not be parsed and was not treated as clean. |
| Uptime Kuma | 4 confirmed; 21 suspected | 4 useful leads; 17 expected benign matches; 4 confirmed facts | Dynamic shell boundaries and disabled TLS verification deserve review; most shell calls are fixed maintenance commands; four helper manifests lack lockfiles. |
| Mealie | 0 findings | no finding to classify | No configured pattern matched. This is not evidence that the application is secure. |

## Useful-lead boundary

- A lead names the exact file and construct to inspect. It does not prove attacker-controlled input,
  runtime reachability, deployed configuration or exploitability.
- Open WebUI's two `exec(content)` paths are intentional plugin/function execution. The remaining
  question is who can author or enable that content and whether the trust boundary matches the
  product policy.
- Uptime Kuma exposes an operator-selected unsafe TLS option and retains a deprecated healthcheck
  that globally disables verification. Their deployed use was not established.
- Healthchecks' four HTML sinks receive server responses. Source-only review did not follow every
  response producer and encoding contract, so the leads stay suspected.

## Confirmed-fact boundary

The four Uptime Kuma `dependency-lockfile-missing` findings confirm only that the named example or
helper manifests have no adjacent or workspace-applicable lockfile. They do not prove dependency
compromise, package reachability or an exploitable application vulnerability.

## Reproduction

Use clean checkouts at the commits in the structured evidence, then run the built-in adapter with a
fixed timestamp. No target dependencies are required:

```bash
WEBAPP_SECURITY_FIXED_TIME=2026-08-14T00:00:00.000Z \
  node scripts/webapp-security.mjs audit /path/to/clean-checkout \
  --adapter builtin --fail-on never --out /private/output-directory
```

Compare each `report.json` SHA-256 with `v0.5.0-evidence.json`. A different source commit, ruleset
digest, traversal limit or tool version is a new observation, not a rewrite of this review.
